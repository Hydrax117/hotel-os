# Hotel OS image upload wiring (backend + frontend)

The change wires end-to-end image management for hotel properties: a NestJS backend adds four guarded endpoints backed by `ImagesService` (ownership-checked, Supabase admin SDK for storage deletion), and the frontend adds a Supabase browser client helper, an images API module, a reusable `ImageUploadSlot` component, and updates to the dashboard profile page and onboarding step-5. The approach is a thin REST layer over Prisma + Supabase Storage, with the frontend uploading directly to Supabase and then saving the resulting public URL to the backend.

Watch for: the `onboarding` category is hardcoded as the Supabase `hotelId` path segment in step-5, meaning all onboarding images land at `onboarding/<slotId>/…` regardless of user — no per-user isolation; confirmed.

**Verdict**: APPROVED

## High-level view

All four backend endpoints are guarded by `JwtAuthGuard + RolesGuard(HOTEL_OWNER)` and every service method calls a shared `verifyOwnership` helper before touching data, so there is no path to read or mutate another owner's images. The ownership check throws `ForbiddenException` on mismatch and `NotFoundException` on a missing hotel, giving correct HTTP semantics.

The `ImageUploadSlot` component validates MIME type and size before uploading, clears loading state in a `finally` block on both upload and delete paths, and exposes error text below the slot on failure — the spec requirements are all met. The only gap worth noting is that the file input's `accept` attribute restricts the browser picker but the real enforcement is the `file.type` check in JS.

The onboarding step-5 handler is correct in shape: upload first, then pass the URL (or `''` on failure) to `updateImageSlot`. The `ImageSlot.preview` field is typed `string | null`, and the handler always passes a `string`, so no `undefined` can leak into the context. The one structural gap is that all onboarding uploads share the path prefix `onboarding/` with no user identifier, so concurrent onboarding sessions from different users could theoretically collide on UUID paths (extremely unlikely, but worth noting for a production hardening pass).

## Ownership checks across all four service methods

`verifyOwnership` is a private helper that fetches the hotel by ID and compares `hotel.ownerId` to the caller's `ownerId`. All four public methods — `getImages`, `addImage`, `deleteImage`, `setPrimary` — call it as the first operation. `deleteImage` and `setPrimary` also fetch the individual image record and throw `NotFoundException` if it is absent, so a valid owner cannot accidentally trigger a 500 on a bad image ID.

The `deleteImage` path uses `indexOf` to locate `/object/public/<bucket>/` in the stored URL and extracts the storage path from that position. If the marker is not found (e.g., a URL stored from a different storage provider), it skips the Supabase `remove` call and proceeds directly to the Prisma delete — the DB record is cleaned up even if the storage object is orphaned. This is a reasonable degraded-path choice.

## MIME and size validation

`ImageUploadSlot` validates before setting `loading=true`: size check first, then MIME type check against `['image/jpeg', 'image/png', 'image/webp']`. Both branches set `errorMsg` and return early without touching the network. On upload error or delete error the `finally` block clears `loading`, so the spinner never gets stuck. The file input's `accept="image/jpeg,image/png,image/webp"` attribute matches the JS validation list.

## Onboarding step-5 URL storage

`handleFileChange` initialises `url = ''`, wraps `uploadImage` in try/catch setting `url = ''` on failure, then calls `updateImageSlot(id, file, url)`. The context's `updateImageSlot` signature is `(id: string, file: File, preview: string)` — the third parameter is `string`, not `string | null | undefined`. The handler always passes a `string` (either the public URL or `''`), so the context never receives `undefined`. The `ImageSlot.preview` field is `string | null`; the context setter assigns it directly, so at worst it is `''` rather than `null` — harmless for downstream consumers.

## Backend: no `any` types, all local imports use `.js` extensions

Every local import in `images.service.ts`, `hotels.controller.ts`, and `hotels.module.ts` carries the `.js` extension required for ESM. No `any` annotation or `as any` cast appears in the new backend files. `SupabaseClient` is typed via `import { type SupabaseClient }` and the private field is `private supabase: SupabaseClient`.

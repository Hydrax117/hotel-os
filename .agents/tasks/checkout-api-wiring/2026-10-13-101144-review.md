# Checkout API wiring: real booking flow, auth gates, bookings page live data

This change replaces all mock data in the checkout, confirmation, and bookings pages with real API calls. The checkout flow now creates a booking via POST, initializes a Paystack payment, and redirects the browser to the payment gateway. The bookings page fetches live data, maps API statuses to UI tabs, and wires cancel actions to the API. The confirmation page is simplified to read all display data from URL params rather than re-fetching from mocks.

**Watch for:** The bookings page `BookingCard` still builds its `detailsHref` with `hotelId` and `roomId` params, but the confirmation page no longer reads those params — it expects `hotelName`, `roomName`, and `total`. Any "View details" link from the bookings page will show `Hotel` and `Room` fallbacks instead of real names. (confirmed)

**Verdict**: NEEDS_CHANGES

---

## High-level view

`app/lib/api/bookings.ts` is a clean, fully-typed API module with four functions and no `any` types. All API status variants are represented in the union type.

The checkout flow correctly sequences `createBooking` → `initializePayment` → `window.location.href`. The auth gate and pre-fill from `useAuth` are both present. Hotel and room data is fetched directly from the API using bare `fetch` calls rather than `apiClient`, with a loading state that shows `—` placeholders. Error handling is present but errors surface silently (the `dataError` path is only shown after `dataLoading` clears, which works correctly given the `finally` block).

The confirmation page's simplification is the right call given that Paystack owns the redirect back — the page is stateless and all data must come from the URL. But the bookings page hasn't been updated to pass the new params (`hotelName`, `roomName`, `total`) to the confirmation link, leaving that navigation path broken.

The bookings page is otherwise complete: auth gate present, real API wired, all `MOCK_TRAVELER_BOOKINGS` references removed, status mapping exhaustive, cancel action wired with optimistic UI update, loading skeleton present.

## Confirmation page URL contract break

The confirmation page was refactored from server-side mock lookup to pure URL-param consumption. The new params are `hotelName`, `roomName`, and `total`. The checkout page never navigates directly to confirmation — it sends the user to Paystack, so that path is fine.

The bookings page `BookingCard` builds its link at line 203:

```
/booking/confirmation?ref=${booking.id}&hotelId=${booking.hotelId}&roomId=${booking.roomId}&checkIn=...
```

`hotelId` and `roomId` are ignored by the confirmation page. The names and total will always render as fallback values (`Hotel`, `Room`, `—`). The fix is straightforward: substitute `hotelName` and `roomName` (both available on `TravelerBooking`) and add `total=${booking.totalNgn}`.

## Bare fetch calls in checkout bypass apiClient

The hotel and room data fetch in `CheckoutInner` uses bare `fetch` calls rather than `apiClient`. This means auth headers are not attached to those two requests. The hotel and rooms endpoints are public, so this is not a functional gap right now, but it's an inconsistency to note — if those endpoints are ever gated, the checkout page will silently fail to load room data for authenticated users.

## Status mapping exhaustiveness

`mapStatus` in `app/bookings/page.tsx` handles all seven API status variants (`HELD`, `CONFIRMED`, `CHECKED_IN`, `CHECKED_OUT`, `CANCELLED`, `PAYMENT_PENDING`, `NO_SHOW`, `PENDING`). TypeScript will catch any new variant added to `ApiBookingStatus` that isn't handled.

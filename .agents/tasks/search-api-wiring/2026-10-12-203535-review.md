# Search API wiring — mock data replaced, real API connected

SearchResults, the hotel detail page, and the homepage now fetch from `https://hotel-os-api-52qe.onrender.com` instead of local mock arrays. The approach introduces a `serverFetch` helper for server components and delegates to `apiClient` for the authenticated client-side search. The hotel detail page drops `generateStaticParams` and gates on a null return from `fetchHotelDetail` to call `notFound()`. Build passes clean with no TypeScript errors.

Watch for: `searchHotels` calls `apiClient` which attaches the user's auth token — unauthenticated visitors to `/search` will hit a 401 and see the error state rather than results (confirmed). The retry button in the error state resets `loading` to `true` but does not re-trigger the `useEffect`, so the retry has no effect (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The `serverFetch` / `apiClient` split is architecturally correct: server components use bare `fetch` with `no-store`, client components go through the authenticated axios interceptor. `instant = false` on both the homepage and the hotel detail page satisfies the `cacheComponents: true` constraint in `next.config.ts` without reaching for the banned `export const dynamic`.

The hotel detail page calls both `fetchHotelDetail` and `fetchHotelRooms` in parallel, guards on `detail === null` with `notFound()`, and null-coalesces every optional array field (`detail.amenities ?? []`, etc.) before rendering. The rooms-fetch failure is silent (returns `[]`), which is a reasonable trade-off since the page still renders without room cards.

The SearchResults loading, error, and empty states are all present. The pagination math (`page * 12 >= total`) correctly mirrors the previous `sorted.length <= 12` logic that was there before. The one structural bug is the retry button: it sets `loading: true` and clears the error, but `useEffect` only re-fires when its dependency array changes — `page`, `destination`, etc. haven't changed, so the effect never runs and the user is stuck on the now-blank state.

The homepage falls back to static `FALLBACK_HOTELS` and `FALLBACK_DESTINATIONS` when the API returns empty arrays, which means a cold Render spin-up won't leave the page blank.

<summary>Details</summary>

### Retry button dead-end

The error state renders a "Retry" button that calls:

```ts
setPage(1);
setError(null);
setLoading(true);
```

`setLoading(true)` causes a re-render but not a new fetch — `useEffect` only fires when a dependency changes. If the user is already on page 1 (which they will be after hitting an error on the first load), none of the dependencies change and the effect never runs. The `loading` flag is set to `true` but nothing sets it back to `false`, leaving the component stuck in the loading skeleton with no visible error. Incrementing a `retryCount` state variable in the dependency array would fix this in one line.

### Auth requirement on public search

`apiClient` is the axios instance created in `app/lib/api/client.ts`. Its request interceptor reads `localStorage.getItem('token')` and attaches it as `Authorization: Bearer …`. A visitor who hasn't signed in has no token, so every `searchHotels` call will return a 401 from the NestJS backend. The error state will show the 401 error message, but this is a poor experience for a page that's supposed to be a public hotel discovery tool. The fix depends on a backend decision: either the `/api/v1/hotels` endpoint needs to allow unauthenticated requests, or the frontend needs to route search traffic through a server action that uses `serverFetch` (which carries no auth token).
